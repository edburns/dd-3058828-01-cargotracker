## Implement

Modify only:

- `src/main/java/org/eclipse/cargotracker/application/BookingService.java`
- `src/main/java/org/eclipse/cargotracker/application/internal/DefaultBookingService.java`
- `src/test/java/org/eclipse/cargotracker/application/BookingServiceTest.java`

Add this application API:

```java
void changeDeadline(TrackingId trackingId, Date deadline);
```

Implement it in `DefaultBookingService` by:

1. Loading the aggregate with `cargoRepository.find(trackingId)`.
2. Reading the current destination from `cargo.getRouteSpecification().getDestination()`.
3. Creating a new `RouteSpecification` with `cargo.getOrigin()`, the current destination, and the supplied deadline.
4. Calling `cargo.specifyNewRoute(routeSpecification)`.
5. Calling `cargoRepository.store(cargo)`.
6. Logging the tracking ID and new deadline at `Level.INFO` in the style of `changeDestination(...)`.

Write `testChangeDeadline()` first and place it after `testChangeDestination()` in the existing ordered test sequence. Build a deadline one month after the test's original `deadline`, invoke the service, reload using `Cargo.findByTrackingId`, and assert all of the following:

- origin remains Chicago;
- destination remains Helsinki;
- the stored deadline is the same calendar day as requested;
- the assigned itinerary is unchanged;
- transport status remains `NOT_RECEIVED`;
- last known location remains `Location.UNKNOWN`;
- current voyage remains `Voyage.NONE`;
- the cargo is not misdirected;
- estimated time of arrival is `Delivery.ETA_UNKOWN`;
- next expected activity is `Delivery.NO_ACTIVITY`;
- the cargo is not unloaded at destination;
- routing status remains `MISROUTED`.

Use calendar-day comparison consistent with the existing historical test style; do not introduce a timezone policy.
