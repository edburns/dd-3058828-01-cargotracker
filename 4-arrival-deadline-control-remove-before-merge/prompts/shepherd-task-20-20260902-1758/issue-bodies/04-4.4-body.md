The resolved decisions are binding:

- Mirror the Change Destination interaction with a serializable JSF managed `@SessionScoped` launcher named `changeArrivalDeadlineDateDialog`; the CDI view-scoped editor is already present from Issue 3.
- Open `/admin/dialogs/changeArrivalDeadlineDate.xhtml` with one `trackingId` request parameter. Options are `modal=true`, `draggable=true`, `resizable=false`, `contentWidth=410`, and `contentHeight=280`.
- Successful submission closes with `"DONE"`; cancellation closes with `""`. A `dialogReturn` handler supports refreshing `tableNotRouted`.
- Put `<f:metadata>` directly under root `<html>`, before `<h:head>` and `<h:body>`, because MyFaces requires view metadata at `UIViewRoot` scope.
- Require a date but add no new chronological business rule.
- Open Liberty package/start, HTTP checks, and browser behavior are mandatory; do not modernize the historical remote-Payara Arquillian runtime.

Research established that incorrect metadata nesting causes MyFaces `TagException`/parent-component failures and that the prepared baseline intentionally places metadata at the view root. Preserve that structure. Implement the dialog from production patterns and the contract above, not research artifact source code.

## Implement

Create:

- `src/main/java/org/eclipse/cargotracker/interfaces/booking/web/ChangeArrivalDeadlineDateDialog.java`
- `src/main/webapp/admin/dialogs/changeArrivalDeadlineDate.xhtml`

The launcher must be serializable and use:

```java
@ManagedBean(name = "changeArrivalDeadlineDateDialog")
@SessionScoped
```

Implement `showDialog(String trackingId)`, `handleReturn(SelectEvent event)`, and `cancel()`. Follow the adjacent destination-dialog production pattern while applying this issue's explicit contract:

- create the five exact dialog options above;
- pass `trackingId` through `Map<String, List<String>>`;
- open `/admin/dialogs/changeArrivalDeadlineDate.xhtml`;
- close cancellation with an empty string and never call the facade from `cancel()`;
- preserve a return handler suitable for the caller's `dialogReturn` Ajax event.

The XHTML title must be `Change Deadline`. Put this metadata directly beneath root `<html>` and before `<h:head>`:

```xhtml
<f:metadata>
    <f:viewParam name="trackingId"
                 value="#{changeArrivalDeadlineDate.trackingId}"/>
    <f:viewAction action="#{changeArrivalDeadlineDate.load}"/>
</f:metadata>
```

Build a labeled form that displays:

- `Origin:` with `#{changeArrivalDeadlineDate.cargo.originName}`;
- `Destination:` with `#{changeArrivalDeadlineDate.cargo.finalDestinationName}`;
- `Deadline:` with a required `p:datePicker` bound to `#{changeArrivalDeadlineDate.arrivalDeadlineDate}`;
- **Cancel** invoking `#{changeArrivalDeadlineDateDialog.cancel()}`;
- **Update** invoking `#{changeArrivalDeadlineDate.changeArrivalDeadline()}`.

Provide visible validation feedback associated with the date input. Do not close on failed validation or failed facade delegation. Keep the caller-refresh contract compatible with the existing destination dialog; actual table wiring remains Issue 5.

## Completion gates

- `.\mvnw.cmd clean package -Popenliberty liberty:run` starts successfully on JDK 17.
- A direct request to `http://localhost:8080/cargo-tracker/admin/dialogs/changeArrivalDeadlineDate.xhtml?trackingId=DEF789` returns HTTP 200.
- The direct view renders title **Change Deadline**, origin, destination, and the existing selected deadline.
- Server and page evidence contains no `TagException`, `Parent UIComponent`, `FacesException`, or feature-caused server error.
- Cancel leaves the persisted deadline unchanged.
- Update changes the deadline, closes only after success, and a repeated direct load initializes to the changed value.
- Existing destination editing still works.
- Stop Liberty cleanly before completing the issue.
