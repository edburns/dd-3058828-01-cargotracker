PR [#24](https://github.com/edburns/dd-3058828-01-cargotracker/pull/24) contained the expected implementation but omitted that evidence. This was a hard completion gate, not an optional documentation preference. Stage 30 therefore could not declare the task ready.

### 7.2 Immediate Failure Mechanism: Completed CCA Cycle Without a Push

The shepherd submitted a concrete requested-changes review describing every missing item. GitHub recorded both the subsequent CCA start and finish events, but the PR HEAD stayed at `1d3986e`. After ten minutes without a new HEAD, stage 30 emitted:

The terminal failure was: **Copilot completed a follow-up work cycle on PR [#24](https://github.com/edburns/dd-3058828-01-cargotracker/pull/24) but did not push a new HEAD within 10 minutes.**

No reassignment was attempted because Copilot re-engaged organically. The logs do not reveal why that work cycle produced no commit, so a deeper CCA-side cause cannot be established from local artifacts.

### 7.3 Stage-40 Propagation

Stage 40 found zero CCRA findings and zero unresolved CCRA threads on the unchanged HEAD. That clean CCRA result did not supersede stage 30: the required acceptance evidence was still absent and the local requested-changes review remained valid. Stage 40 correctly stopped without merge and restored draft state.

### 7.4 Exit-Code Observability Gap

Every individual exported JSONL `result` event reports process exit code `0`, including both sessions for [#14](https://github.com/edburns/dd-3058828-01-cargotracker/issues/14). The semantic failures are present only in the assistant outcome text and final GitHub state. The outer manifest correctly records campaign exit code `1`. Automation that reads only per-session process exit codes would misclassify the final task as successful.

- The final task had the broadest user-visible acceptance matrix: server startup, HTTP rendering, browser state transitions, persistence, cancellation, regressions, logs, shutdown, and a final build.
- Evidence was expected to be added to the PR body by CCA rather than captured independently by the shepherd.

## Section 8: Observations and Recommendations

### 8.1 What Worked

- The ordered, serial campaign preserved base-branch dependencies and merged four tasks cleanly.
- Stage 30 applied strong fail-closed gates for linkage, HEAD stability, substantive CI, runtime behavior, and acceptance evidence.
- CCRA convergence was high: four first-pass clean reviews and one defect corrected in a single follow-up round.
- Stage 40 did not mistake a clean CCRA review for proof that all issue requirements were met.
- Failure cleanup was safe: PR [#24](https://github.com/edburns/dd-3058828-01-cargotracker/pull/24) remained open, mergeable, and draft against the correct non-`main` base.

### 8.2 What Failed

- CCA did not record the final task's mandatory acceptance evidence before declaring its initial cycle complete.
- The requested follow-up cycle made no observable PR change.
- Per-session process exit codes did not represent semantic shepherd failure.
- Exact token accounting was unavailable because usage fields were redacted.

### 8.3 Recommended Improvements

1. **Make semantic outcome machine-readable.** Have stages 30 and 40 write a small result artifact containing `status`, `failureCode`, issue, PR, reviewed HEAD, and terminal reason. The outer script should consume this instead of relying on CLI process exit alone.
2. **Use a specific no-op-cycle failure code.** Classify the [#14](https://github.com/edburns/dd-3058828-01-cargotracker/issues/14) signature as `cca_followup_completed_without_head_change`, including start/finish timestamps and unchanged SHA.
3. **Add one bounded retry for no-op CCA cycles.** Reassign once with a concise checklist when a completed follow-up cycle produces neither a HEAD nor PR-body change. Preserve the current fail-closed behavior after that retry.
4. **Treat PR-body changes as progress.** Acceptance evidence can be added without a code commit. The wait gate should compare both HEAD and a stable hash or update timestamp of the PR body before classifying a cycle as a no-op.
5. **Front-load acceptance checklists.** For browser-heavy tasks, include a copy-ready PR-body evidence template in the issue or assignment prompt so CCA can fill measured values during its initial run.
6. **Separate code-review and acceptance-review metrics.** Report CCRA rounds/comments independently from local requested-changes gates; this run shows that code-review convergence can be clean while acceptance remains blocked.
7. **Preserve comparable lesson-mode metadata.** Continue recording `lessonPropagation: off` in manifests and reports so this control run can be compared directly with lesson-enabled campaigns.
