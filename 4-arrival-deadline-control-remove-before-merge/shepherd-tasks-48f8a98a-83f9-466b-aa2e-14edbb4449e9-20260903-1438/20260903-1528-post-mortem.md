## Section 8: Observations and Recommendations

### 8.1 What Worked Well

- **Fail-closed campaign validation:** Campaign ID, repository, base branch, metadata directory, lesson mode, task linkage, PR head, checks, review state, and merge target were explicitly verified.
- **Strong acceptance evidence:** Stage 30 did not accept CCA's incomplete browser evidence. It ran the application locally with JDK 17 and automated the complete `DEF789` flow.
- **Effective review convergence:** One low-severity CCRA finding required one small commit and one follow-up review.
- **Safe isolation:** Both phases used detached worktrees and preserved unrelated untracked campaign artifacts in the control worktree.
- **Runtime-aware validation:** Transient JMS startup warnings were checked through eventual endpoint activation rather than treated as either automatic success or failure.
- **Control-campaign integrity:** `lessonPropagation: off` remained consistent in campaign metadata, invocation, and run manifest.

### 8.2 What Could Be Improved

- Stage 30 spent roughly 30 minutes waiting for a CCA lifecycle event whose timestamp changed from local-looking `14:33:31` to UTC `22:05:11`. Normalizing event timestamps before comparison and display would reduce ambiguity.
- Browser automation required three selector-debug iterations. The temporary script was effective, but stable helper conventions for PrimeFaces dynamic dialogs, direct-link text, overlay dismissal, and visible iframe selection would reduce repeated work.
- Stage 40 invoked Maven under JDK 25 against a Java 7 source-level project even though stage 30 had already established JDK 17 as the campaign runtime. Validation should carry the campaign's proven Java runtime contract forward.
- The task JSONL captures AIU but redacts complete input/output token counts. Post-mortem tooling should treat AIU, premium requests, cache tokens, and model tokens as separate metrics rather than expecting a single token field.

### 8.3 Actionable Recommendations

1. **Persist phase summaries:** Have stages 30 and 40 write a compact machine-readable summary containing phase start/end, issue, PR, head SHA, review IDs, findings, fix commits, merge result, and validation commands. This would avoid reconstructing metrics from large Markdown exports.
2. **Normalize timestamps:** Convert all GitHub timestamps to UTC for comparisons and to one declared local zone for display. Include both only when diagnosing lifecycle anomalies.
3. **Reuse runtime metadata:** Record the validated JDK and build command in the stage-30 output, then require stage 40 to reuse that environment for local checks.
4. **Add PrimeFaces browser helpers:** Maintain reusable automation helpers for the visible dynamic-dialog iframe, date-picker overlay dismissal, Ajax table refresh, and component IDs with JSF naming-container prefixes.
5. **Classify transient command failures:** Distinguish probe/automation errors from campaign failures in the run summary. This campaign had seven recoverable command failures but no failed gate.
6. **Export unredacted aggregate token counters when policy permits:** Aggregate input/output counts can be retained without preserving message content. If unavailable, continue reporting AIU and premium requests explicitly rather than estimating tokens.

### 8.4 Overall Assessment

The campaign achieved its requested outcome with strong end-to-end evidence and a clean merge. The control run demonstrates successful convergence for a small, well-scoped UI integration task: CCA supplied the implementation, local shepherding closed the acceptance-evidence gap, CCRA caught one minor presentation defect, and the local CLI resolved it without broadening scope. The main optimization opportunity is operational efficiency in lifecycle waiting and browser-test setup, not product correctness.
